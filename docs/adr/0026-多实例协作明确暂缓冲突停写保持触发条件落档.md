# ADR-0026:多实例协作明确暂缓——冲突停写机制保持,触发条件落档

日期:2026-09-30 · 状态:已采纳(册七 D-G3,动工前落库)
关联:册七迭代计划 D-G3/T7.6 · ADR-0010(个人自用,以使用频率为准)· ADR-0017(延后评估框架先例)· ADR-0021(V3 布局与 OpLog 完整性)· 既有锁语义(lock.rs 排他写锁 + 停写)

## 背景

册七 T7.6 的决策点 D-G3:两个进程/两台机器同时打开同一工程(多实例协作)要不要
做。现状已有**单机多实例防护**:工程级排他写锁(`.cutforge/lock`,活进程持锁 →
第二个写者拒绝)+ 常驻同步守护(外部改动 ≤1s 可见,SSE 通知)+ 冲突停写(检测到
外部改动与本地未落盘改动交汇 → 停写并要求人工裁决)。真正缺失的是**双写合并**
(两个实例各自产生 Op 序列的意图合并)与跨机会话感知。判定准绳(ADR-0010 框架):
个人自用无"两台机器同时剪一个工程"的真实用例——单人多机 usage 模式是"时间错开,
拷贝/打包搬运"(T7.6 的 .cfpkg 正是这个形态),不是"同时在线协作"。

## 决策

1. **多实例协作(双写合并/跨机会话)明确暂缓,不做**:册七不实现任何 OT/CRDT/
   意图合并机制;现有防护面原样保持——排他写锁、外部改动三路合并、冲突停写。
2. **现有锁语义不为此复杂化**:不引入共享读锁升级、不搞锁租约/watchdog 心跳、
   不给锁加属主标识——锁只回答"能不能写"一个问题;语义保持简单可审计。
3. **触发重启条件(落档,出现即重新立项 + 逐案 ADR)**:
   - 真实双机需求出现:同一工程需要两台机器在**同一时间窗**内各自改动且人都
     在等对方(拷贝/打包搬运的工作流实测不够用);
   - 或个人工作流演进为"AI 代理 + 人"双写者高频并行,冲突停写的人工裁决频次
     高到成为日常摩擦(以 OpLog/冲突清单的真实记录为准,非想象)。
   触发前,"多实例协作"在能力矩阵与文档落"明确暂缓(触发条件见 ADR-0026)",
   不是"待办"。

## 取舍

- 暂缓 ≠ 否定:OpLog(rev/baseRev/anchor 面自册二起就是按可合并形态设计的)为
  未来协作留了地基,今天的暂缓不烧掉明天的路;但**不为想象中的需求预建合并层**
  ——没有真实冲突样本之前,任何合并语义都是纸面设计,做出来必然返工。
- .cfpkg 打包/解包(T7.6)顺势成为"多机协作"的现实答案:整工程快照搬运 +
  OpLog 随包,时间错开的协作零新增机制。

## 被否决的替代

- **现在就做双写合并**:否决——个人单机无需求(ADR-0010 三指标:无用例、锁语义
  复杂化直接损害现有"简单可审计"的停写纪律、Op 意图合并的实现与验证面巨大);
  为对标 OpenCut 一类团队产品形态打工,违反个人自用取舍。
- **只做"第二只读实例"增强(多窗口只读)**:否决立项——只读打开本就不持锁
  (ADR-0007),多窗口已天然可用;为它建"会话感知"面属于无场景建设。
- **锁语义升级(租约/心跳/属主)**:否决——现有锁的"陈旧可恢复"(library_recover
  残留锁清单 + 恢复)已覆盖崩溃场景,复杂化只增加新失效模式。

## 后果

- T7.6 范围收敛为 .cfpkg 打包/解包 + 分享导出说明;协作文档如实写"单写者 +
  时间错开搬运"模型。
- 冲突停写/排他锁的行为零变化,既有测试面(http_hardening/e2e_events/依赖锁的
  写路径单测)全部不动。
- 触发条件出现时,从 OpLog 形态出发重新立项(届时 OpLog 的 anchor/baseRev 已有
  真实冲突样本可供设计输入),不受本决策约束。
