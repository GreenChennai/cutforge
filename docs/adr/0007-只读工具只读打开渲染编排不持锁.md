# ADR-0007:只读工具走只读打开,渲染编排不持 workspace 锁

日期:2026-09-20 · 状态:已采纳(2026-09-20 迭代落地)
关联:ITERATION-PLAN-v2.0 E5/E6-3/B14 · V2-PROGRESS M8-R5 · ADR-0006(可独立起步)

## 背景

M8-R5 已记录:"MCP dispatch 对只读工具也走 `open_exclusive`(防 TOCTOU),长操作(渲染编排)持锁会阻塞并发工具"。E5 已让渲染子进程不持 workspace 锁,但查询类工具仍无条件排他打开——编辑器 UI 高频轮询(时间线/标注/OpLog)与渲染期间的任何并发查询都会被排他锁卡死。"文件是真相源"的架构下,读理应比写宽松。

## 决策

1. **查询类工具走只读打开**(`Workspace::open`,不申请排他锁):project_get / wordline_get / cutlist_get / notes_list / oplog_tail / conflict_list / timeline_get 七个纯查询工具;白名单收口在 dispatch 一处,新查询工具必须显式入列。
2. **渲染编排保持子进程不持 workspace 锁**(E5 语义不变):长操作只在短临界区内读盘,不把锁带到渲染全程。
3. **写操作维持 `open_exclusive` 全程锁**:一切产生 rev 的工具不放松——只读宽松、写排他,不搞全量无锁。

## 取舍

- 只读打开需要接受"读到半写状态"的窗口(TOCTOU):工程文件原子写(唯一落盘点 + 备份)保证读到的要么是旧全量要么是新全量,不存在撕裂数据,但读到的可能比刚完成的写旧一拍。
- 换来:编辑器高频轮询与渲染期间的并发查询不再被排他锁阻塞,"AI 读盘面"与"渲染出片"可以同时进行。

## 被否决的替代

- **全量排他(现状)**:否决——简单,但并发工具互相阻塞,M8-R5 记录的问题原样保留。
- **全量无锁**:否决——写与写并发会产生工程文件分叉风险;锁的收益(串行化写)必须保留。

## 后果

- 查询类新增/下线 = 改一处白名单 + 补并发 e2e;消费者不得假设"查询返回的一定是最新写"(以 rev 自查)。
- 并发语义有了验收判据:渲染期间并发查询不阻塞、结论与串行一致。

## 落地证据

- `crates/cutforge-mcp/src/lib.rs`:dispatch 的 `is_readonly_tool` 分流(E6-3/B14)——七个查询工具走 `Workspace::open` 只读打开,其余写操作仍 `open_exclusive` 全程锁;白名单单点收口,`produces_rev_mutation` 与其共用口径。
- 渲染编排:渲染子进程不持 workspace 锁(E5 既有语义,本决策明文化)。
- e2e:`tools/e2e_from_zero.py` 第 5+6 步「E6-3 渲染期间并发不阻塞」——渲染窗口内并发探测查询,不阻塞且结论一致。
