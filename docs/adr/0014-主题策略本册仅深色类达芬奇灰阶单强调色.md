# ADR-0014:主题策略——本册仅深色(类达芬奇灰阶 + 单强调色),浅色列册七可选

日期:2026-09-29 · 状态:已采纳(册三 D-C1,动工前落库)
关联:册三迭代计划 T3.1/D-C1/AC-3.1 · 册三总纲 §3.C(达芬奇参考对齐)· ADR-0011(无构建 ESM)· tokens.css 三层 token

## 背景

册三 T3.1 要求建立设计系统:三层 token(原始/语义/组件)、零硬编码色值(门禁扫描)、对比度全部 ≥ WCAG AA。动工前的决策点 D-C1:主题策略走「仅深色」还是「深色+浅色双主题」?

## 决策

1. **本册仅深色**。灰阶基底取类达芬奇 video 编辑室的低饱和蓝灰深色系(950→100 十三档),配**单一强调色**(蓝 `--cf-accent`,选中/链接/吸附语义);danger/warning/success/playhead/select 各自独立语义色,不与强调色混淆(播放头红 ≠ 选中金 ≠ 强调蓝)。
2. token 架构为浅色主题预留但**不实现**:原始层(灰阶/色相档位)与语义层(`--cf-bg/panel/elevated/text-*` 等抽象名)分离——未来浅色主题只需换语义层对原始层的映射,组件层与全部组件 css 零改动;门禁(色值扫描)天然保证没有组件绕过这层映射。
3. **对比度是硬约束**:正文 4.5:1、大字/图形 3:1(WCAG 2.1 AA),全部前景/背景组合以脚本计算核对(表见 `docs/design/contrast-table.md` 与 tokens.css 头注释);深色系下尤其盯紧「次级文本/面板」「clip 字/轨面」这类低档组合。
4. canvas 绘制面(标尺/overlay/波形/预览代理)同样零硬编码色值:`js/render/theme.js` 统一经 `getComputedStyle` 读语义 token,与 css 同源(改 token 两面同步)。

## 取舍

- 仅深色把 T3.1 的验证面收敛一半(对比度表、门禁绿、录屏存档都只对一套主题负责),册三工期让位给动效与手势(本册真正的体验瓶颈)。
- 个人自用场景(ADR-0010)下浅色主题无真实需求方;双主题会迫使每个组件从第一天维护两套 hover/glow/阴影态,而册三组件层 token 尚未稳定。
- token 分层使浅色的边际成本后置且可控:预期改动面 = 语义层一份映射文件 + 一轮对比度重算,不含组件 css 与 js。
- 灰阶基底保留表面分层(底/面板/浮层)的表达空间:大面积死灰与单色平面是用户明确的审美否决项。

## 被否决的替代

- **深色+浅色双主题(本册)**:否决——验证面翻倍、组件层 token 未稳定即被两套主题锁死;列册七可选(届时重开 ADR 评审语义层映射方案)。
- **跟随系统主题(auto)**:否决——无浅色实现的前提下等价于仅深色,却引入 `prefers-color-scheme` 分支的测试负担。
- **高对比纯黑(#000 底)主题**:否决——大面积纯黑在长时间剪辑场景加剧视疲劳与 OLED 拖影,且与达芬奇参考的灰阶层级心智不符;灰阶基底保留表面分层(底/面板/浮层)的表达空间。

## 后果

- `css/tokens.css` 是全仓唯一色值定义点(check-shell-purity R5 色值扫描强制:css/js/html 零裸色值,legacy/ 豁免、assets/icons.js 登记豁免);任何新组件先加 token 再引 var。
- 深色假设渗入个别绘制细节(canvas 文字反白、阴影纯黑基)——浅色化时这些点要随语义层一起重审。
- 录屏/截图存档(AC-3.2)只出深色一套。
