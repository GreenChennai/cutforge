# ADR-0025:Editor API 版本策略——URL 版本 /api/v1,旧 /rpc 保留别名

日期:2026-09-30 · 状态:已采纳(册七 D-G2,动工前落库)
关联:册七迭代计划 D-G2/T7.1/AC-7.1 · ADR-0009(纯 std HTTP,不引入框架——版本路由同为手工前缀判定)· ADR-0003(能力矩阵是生成物——OpenAPI 同为生成物,同一纪律)

## 背景

册七 T7.1 把既有 `/rpc`(JSON-RPC 面)提升为版本化 Editor API。要决策的是版本号
**放在哪**:URL 路径(`/api/v1/...`)、HTTP 头(`API-Version: 1`)还是不设版本。
判定准绳:个人自用 + AI 助手场景(ADR-0010),API 消费者是未来的自己、SDK 生成器
与 AI 代理——**可读性/可调试性权重最高**,破坏性变更频率低(册级演进,一年数次),
版本切换成本要求反而不高。

## 决策

1. **URL 版本**:`/api/v1/*` 为版本化 REST 面(工具统一入口 `POST /api/v1/tools/<tool>`
   + 常用查询 GET 别名 `/api/v1/project`、`/api/v1/timeline`、`/api/v1/notes` 等 +
   事件流 `/api/v1/events`);版本前缀是路径第一段,手工前缀判定即可路由,不引入
   框架(ADR-0009 纪律不动)。
2. **版本纪律**:v1 内只做加法演进(新工具/新字段/新端点);破坏性变更(删工具/
   改参数语义/改返回形状的老字段)开 v2 并行挂载,v1 保留一个过渡册期——与 /rpc
   别名的保留策略同构。
3. **旧 `/rpc` 保留为别名至少两册**(册七、册八全期):行为零变化,19 份既有 e2e
   与壳全部继续走 /rpc;迁移完成前不删。`/api/v1` 与 `/rpc` 是**同一 dispatch 单表**
   的两个皮,不存在第二套业务逻辑(M4-1 单注册表双通道纪律自然延伸为"三通道")。
4. **OpenAPI 3.1 描述文件是生成物**(ADR-0003 同纪律):由 `tools/gen_openapi.py`
   从 `schemas/mcp-tools.json`(工具契约单一真相源)生成 `docs/api/openapi.json`,
   `--check` 模式进 CI 防漂移;TS SDK 同理由 `tools/gen_ts_sdk.py` 生成。

## 取舍

- URL 版本的"路径即版本"让每个请求自描述:curl 日志、代理排错、AI 读会话记录时
  版本一眼可见,SDK 生成器按前缀切面零逻辑。
- 版本粒度是**整面**而非逐工具:v1 内加工具不动版本号;不为单个工具的加法改动
  发新版本——发版本只对应破坏性变更。

## 被否决的替代

- **头版本(`API-Version: 1`)**:否决——调试不可见(curl 不带头就打不到指定版本,
  日志/抓包里版本缺席),路由层还要读头做分支,复杂度换不来个人场景的任何收益。
- **不设版本**:否决——Editor API 是对外承诺面(第三方工具 + SDK 生成物),破坏性
  变更没有退路等于每次改动都砸自己的既有脚本;版本化的全部意义在"有退路"。
- **日期版本(`2026-09-30`)或逐资源 semver 版本**:否决——粒度过细,个人自用
  演进节奏下维护多版本并行的成本超过收益;整面 + 两册过渡期已够。

## 后果

- `POST /api/v1/tools/<tool>` 与 `/rpc` 的 `tools/call` 转发到同一 `dispatch_with_actor`,
  工具集差异恒为 0;envelope(`{ok,code,ns,message,data}`)原样透传,HTTP 状态码按
  code 确定性映射(200/400/404/409/503/500),协议字段不因换皮漂移。
- `docs/api/openapi.json` 与 `apps/sdk/cutforge.ts` 均为生成物,新工具落库时跑生成器
  同步(CONTRACT-WORKFLOW 补一步);生成物漂移由 `--check` 门禁拦截。
- 壳(shell)册七仍走 `/rpc`,迁移到 `/api/v1` 由 G2(壳侧)自排期;/rpc 至少保留到
  册八收官。
